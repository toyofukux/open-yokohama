# Open Yokohamaの構想

更新: 2026-09-09。市民の問い・争点から理解を支える体験と、その根拠を維持する公共情報基盤の長期構想です。
本書は長期的な方向性です。提供済み機能や達成済みの品質保証を示すものではありません。
具体的な体験・検証・運営設計は[リデザインプラン](REDESIGN-PLAN.md)、基盤の実行順は[開発計画](PLAN.md)、現在の実装・検証結果は[状態記録](STATUS.md)、採用構成は[ADR](adr/0001-static-public-data-core.md)を参照してください。

## 目的と対象

**横浜の暮らしや将来について気になった問いから、何が起き、何を選ぶ話なのかを理解し、根拠と限界を踏まえて自分の考えを持てるようにします。**

日々の暮らしで時間が限られ、政治・経済の専門資料を読み解く余裕がない状態でも利用できるようにします。
情報を探し、問いを分解し、事実と政策を結び付ける負担を提供側が引き受けます。結論を選ぶことや、判断を保留することは本人に委ねます。
投票権の有無にかかわらず横浜で暮らす人を対象とし、専門知識や日常的な政治への関心を前提にしません。

そのために、横浜の公共情報を「収集 → 構造化 → 接続 → 検証 → 分析」し、問いへの答えを確かめ直せる基盤を作ります。
人口、経済、財政、都市、歴史、行政、政策に関する同じ事実・履歴・出典を、WebとAI向けMCPの両方から利用できるようにします。

中核資産は、機械で読める構造化データと原典へのつながりです。画面やAIモデルが変わっても、横浜について蓄積した知識を再利用できることを目指します。

## 必須の編集原則：中立で冷静に伝える

中立で冷静であることを、全記事・見出し・要約・図表・関連導線の必須条件にします。
サイト自身の結論として「この政策を実施すべき」「この案が望ましい」「この候補を選ぶべき」と勧めません。
事実、確認できる傾向、問題の構造、各案の効果の証拠・負担・成立条件・不確実性を示し、価値の優先順位と政策への賛否は読者に委ねます。

問いには、読者の頭の中にある言葉、または具体的な気づきを生む言葉を選びます。「無償化すべきか」は読者が考える問いとして扱えます。サイトが「無償化すべき」と結論を勧めることとは区別します。
中立性を理由に「どんな選択肢があるか」などの抽象的な題へ置き換えません。読者の切実な疑問や意外な事実を入口にし、本文で問題の構造・根拠・複数の選び方を冷静に説明します。驚きをつくるために事実を誇張したり、結論を先取りしたりしません。

条件付きの説明でも、推奨する結論へ誘導しません。「この価値を重視するならこの案がよい」と評価を代行せず、各案で何が変わり、何が残るかを同じ比較項目で説明します。
第三者の「こうすべき」という主張を扱う場合は、発言者・時点・出典を示し、サイト自身の判断と区別します。確認していない集団の賛否・利害を創作しません。

中立性のために、根拠の強い事実と根拠のない主張を同等には扱いません。同じ検証基準を適用し、誤りは訂正します。

中立性は、各文の後に否定や留保を足すことではなく、何が課題で、誰に何が変わり、どの利益・負担・優先順位の調整が必要かを正確に示すことで保ちます。主張の意味を決める対象・時点・仮定は本文や図の近くに残し、調査方法の詳細・誤読への補足・長い出典は注記へ置きます。注記を読まないと主張が誤りになる書き方はしません。
扇情的な言葉、根拠のない危機感、善悪の決め付け、見出し・図の色・並び順による賛否の誘導を避けます。重要な不利益やリスクも、確認できた範囲で具体的に伝えます。
これは内容の編集原則です。現在の全記事が適合確認済みであることを意味せず、既存記事の再レビューにも適用します。

## 選挙や暮らしの問いから、判断材料へ

選挙は、横浜の政治・経済を自分と関係するものとして考える重要な機会です。
選挙で関心を持った争点から必要な材料へ進む体験を重視し、暮らしの違和感や街への好奇心からも同じ問いへ入れるようにします。
ここでの争点は、公共の選択について判断が分かれる具体的な問いです。人口・財政等の分野名は、その問いを調べるための分類として使います。

```text
気になった争点・暮らしの問い
  → 何を判断する話か、ここまで何が分かるか
  → 判断を分ける条件・選択肢・負担・実施権限
  → 必要な下位の問いと具体的な答え
  → 比較・主張・原典の該当箇所
  → 元の問いで分かったこと、残る条件、次に確かめること
```

たとえば公共施設の更新を考えるなら、近さ、機能、将来の利用、費用の関係を示し、人口の将来像等の下位の問いへ進めます。
人口を調べた後も、それだけで施設の必要性は決まらず、利用実態や移動条件等の確認が残ることを元の問いに戻して説明します。
これは設計例であり、特定の選挙の争点や施設の問題を確認した記述ではありません。

選挙後も同じ問いを、意思決定・予算・実施・結果へつなげて維持します。選挙時点の説明と現在の説明を版で区別します。

個別政策の説明から、政策間の優先順位を考える別のページへ接続します。
「どれも必要」で終わらず、具体的にいくらの財源を何に向け、誰にどんな便益があり、何を見送るかを示します。
比較では、同じ年度の正味追加費用、毎年必要な費用と一時費用、使途が決まった財源と配分を変更できる財源を分けます。
同額の予算を自由に振り替えられるとは仮定せず、事業間の依存や法令・契約上の制約、効果の不確実性も明示します。
財源の総額だけで優先順位を自動採点せず、何を重視すると判断が変わるかを読者が考えられるようにします。

選挙種別・対象地域・権限を確認し、全国の問題を市だけで解決できる話として見せません。
読者が運営者と同じ結論に至ることや、特定候補・政党への支持を成果としません。

## コンテンツ全体の役割

サイト全体では、暮らしの具体的な選択、政策間の財源配分、判断に必要な基礎、決定後の点検をつなぎます。
中心に置くのは「横浜で暮らし続けるために、限られたお金・人・土地・時間を何に使うか」です。
費用だけで優先順位を決めず、権利、安全、公平性、最低限のサービス、実行能力も判断条件として扱います。

人口・世帯・密度等は、判断を支える共通の材料です。データの存在だけを理由に記事を作らず、どの問いへの答えを前進させるかを先に決めます。
問いへの具体的な答えを持たない旧記事は撤去・統合し、原典と検査済みデータは再利用できるように維持します。
全領域を同じ画面にそろえることや記事数を増やすことより、問いのつながりと答えの更新を優先します。
具体的な打線と制作順はREDESIGN-PLAN第6.6節に置きます。選挙は期間限定の入口で、サイト全体の分類や存続理由を選挙だけに限定しません。
2026-09-07: このプロジェクトの目的に、横浜市域の公開情報を蓄積するDWHの整備を明記します。
共通基盤に数字・文書上の事実・出典・改定履歴を保持し、open.yokohamaの記事・図表・Webと調査・MCPが参照します。
公開記事は使用したデータ・引用・計算の版を固定し、更新型画面はビルド時の公開版を使います。
現状と目標の差分は[監査](DWH-AUDIT.md)、段階的な移行と受入条件は[DWH設計](DWH-DESIGN.md)にまとめます。人口分野の共通台帳・不変版・19記事の参照は実装済みです。政策記事の文書ファクトと費用の共通化は未完了です。

## 市民が解けるようにしたい問い

上位の問いの例は「子育ての負担を減らすには何を優先するか」「移動手段をどう維持するか」「公共投資を何と比べて評価するか」です。
実際に扱う問いは、利用場面・公共的重要性・根拠・維持可能性を確かめて選びます。以下の個別の問いを、その判断材料として接続します。

- 横浜市の人口はどう変わり、出生・死亡・転入・転出はそれぞれどの程度影響していますか。
- どの区で子どもや世帯が増え、暮らしの条件はどう異なりますか。
- 市税収入や子育て予算は長期的にどう変わりましたか。
- 政策は誰がいつ決定し、どの予算で実施され、成果は確認できていますか。
- 神戸・福岡などの都市と、同じ定義の指標で比べると何が違いますか。
- 横浜の都市史や過去の行政判断は、現在の課題にどうつながっていますか。
- 選挙の投票率や集計結果は、時期・地域によってどう変わりましたか。

問いに含まれる仮説を事実として扱わず、確認できない理由や因果関係は未確認として示します。

## 設計原則

1. **原典を優先します。** 説明から主張、引用、出典、原本へ遡れるようにし、AIの生成文章を一次資料として保存しません。
2. **事実・解釈・提案を分けます。** 反証、留保、未確認事項も表示し、解釈を確定した事実に見せません。
3. **時間を保持します。** 観測時点、有効期間、公表日、取得日、改定番号を区別し、訂正前の状態を再現できるようにします。
4. **地理を保持します。** 横浜市と18区から始め、必要な資料が整えば町丁や生活圏へ拡張します。市平均だけで地域を説明しません。
5. **数字の条件を残します。** 値、単位、期間、地域、定義、算出方法、出典、取得日時を組にします。
6. **構造化データを正本にします。** 大量のPDFをLLMに渡すだけでデータ基盤とせず、数値は決定的なパーサーで抽出します。
7. **問いに具体的に答えます。** タイトルが約束した対象・期間・粒度で答え、一般的な読み方の説明だけで置き換えません。深掘りせずに読了しても価値を得られるようにします。
8. **問いと材料の関係を示します。** 必要な比較を選んだ理由と、そこから言えること・言えないことを説明します。知識を自力で組み立てられることを前提にしません。
9. **判断の自律性を支えます。** 選択肢に同じ検証基準を適用し、異なる立場の利点・負担を示します。根拠の強弱や価値判断の違いを隠さず、編集の利害と訂正を開示します。

## 共通データと公開インターフェース

```text
公式資料 → 不変の原本 → 検査済みの構造化データ
                              ├ 公開Web / CSV / JSON
                              └ 読み取り専用MCP
```

WebとMCPで指標の定義・出典・問い合わせ処理を共有します。公開側には検証済みの公開データだけを渡します。
現在の静的配信と更新時処理を基準とし、初期構想の技術候補を導入要件にはしません。
常時DB、専用検索基盤、Graph DB、任意のAI質問機能は、実際の需要・費用・運用条件が整った段階で判断します。

## データモデルの方向性

以下は拡張時の概念モデルです。すべての項目が現在のスキーマに存在するわけではありません。

| 対象 | 残す情報・関係 |
|---|---|
| Geography | 地域ID、種別、名称、親地域、自治体コード、境界、有効期間 |
| Source | 提供者、資料名、原典URL、資料種別、利用条件、公表日、取得日 |
| SourceSnapshot | 出典ID、内容ハッシュ、保存先、形式、パーサー版、取得日 |
| Citation | 原本の版、ページ、節、表、行、セル、引用箇所 |
| Claim | 主張、事実・解釈・提案の区分、検証状態、有効期間、支持・反証の引用 |
| MetricDefinition | 指標ID、名称、説明、単位、定義、算出方法、資料系列 |
| Observation | 指標、地域、期間、値、原本の版、改定番号 |
| Issue | 課題・争点、判断対象、掲載理由、選択肢、判断条件、状態、時間軸、関連する事実 |
| Question / PageContract | 主質問、利用場面、読後成果、答え、主親・関連問い、元の争点への意味、扱わない範囲 |
| ComparisonSpec | 比較対象・理由、期間、地域、測定種類、定義、分母、変換・計算方法 |
| Review / Release / Correction | 本文・データ・計算・比較を固定した版、確認者・範囲・期限、訂正と影響 |
| Policy | 政策、提案主体、目的、仕組み、状態、実施期間 |
| BudgetProgram | 年度、会計、部局、事業、予算、決算、財源 |
| Decision | 決定主体、日付、議題、種別、結果、政策・予算・課題との関係 |
| Election / ElectionResult | 選挙種別、日付、地域、投票率、候補者別の公開集計結果 |
| Event | 都市史の出来事、日付、分類、説明、課題・政策との関係 |
| CityBenchmark | 比較都市、指標、期間、値、出典、定義の比較可能性 |

政策・予算・成果や都市史・課題の関係には根拠を付けます。単なる同時発生から因果関係を確定しません。
選挙結果・投票率のデータは、公開集計値の記述的・歴史的な比較に用います。有権者個人の情報や政治的嗜好の推定値を保持しません。
公共政策の争点を理解する体験は現在の問いも扱い、結果集計の機能とは区別します。問いの関係も構造化し、同じ証拠を複数の問いから再利用します。

争点の見取り図は必要な枝だけを開けるようにし、データや地域を選ぶ前にも一つの具体的な答えを示します。

## 公開MCPの方向性

市、区、課題、指標、予算、都市史などをリソースとして参照できるようにします。
ツールは公開情報の検索・取得・比較・検証を対象とし、Webと同じデータを返します。

- 知識: 争点・問い・出典・引用の検索、問いの関係と主張から根拠への追跡。
- データ: 指標と時系列の取得、地域・都市比較。
- 財政・行政: 予算比較、議会記録の検索、意思決定・政策の履歴取得。
- 選挙: 公開結果と投票率の記述的比較。
- 検証: 支持資料・反証資料の検索、資料の鮮度確認。

これらは将来の拡張候補です。現在のツールと接続方法は[MCP手順](runbooks/mcp.md)に記載します。
MCPの仕様・バージョン交渉は採用SDKに従い、初期構想で挙げた日付を仕様保証として固定しません。

## 収集・検証・公開

```text
出典台帳 → 取得 → 原本保存 → 解析 → 定義統一
       → 実体・主張・数値の抽出 → 検査 → 必要な人間レビュー → 公開 → 更新監視
```

原本は上書きせず、同一URLの更新も別の版として保存します。処理は再実行可能にし、欠測、重複、形式変更、参照不整合、過去値の改定を検出します。
確認状態は、未確認・機械確認・人間確認・異議あり・廃止を区別します。機械照合を人間の確認として表示しません。

資料は横浜市・神奈川県・政府統計などの一次資料を優先し、研究機関、報道、企業・団体等の資料は性質を明示します。
出典の権威だけで主張を正しいと判断せず、引用箇所が主張を支えているか確認します。

将来のAI回答は、型付きツールを通してデータを参照し、回答・事実・分析・不確実性・反論・引用を分けて返します。
生成後は別プロセスで主張、引用、矛盾、鮮度を確認します。重要な事実主張すべてに根拠を付けることを目標とし、根拠不足なら未確認とします。
政策・因果説明・法的判断・公式発表・対外回答・財務情報のAI生成文は、人間の承認を経て公開します。

問いごとに公開担当と確認期限を持ち、本文・データ・計算・比較条件を一体の公開版として管理します。
重要な変更では確認をやり直し、関連する要約・図表・根拠まで更新します。確認できない新版は公開せず、既存版も誤っている場合は警告・停止します。
維持できない場合は問いの範囲を縮小し、更新終了と最終確認日を明示します。

## 品質と運用の目標

- コード: lint、型検査、必要な単体・統合・E2E、依存関係の検査を行います。
- データ: スキーマ、重複、出典、参照整合性、原本との一致を公開前に検査します。
- AI: 導入時に引用・事実性・検索・ツール選択の評価と回帰テストを整備します。
- 運用: 取得失敗や検証失敗を可視化し、問い合わせから参照データ・出典まで追跡できるようにします。
- 設計判断: 重要な判断、理由、見直し条件をADRに残します。

初期構想の性能目安は、公開ページLCP 2秒未満、API p95 300ms未満、検索p95 1秒未満、AIの最初の有用な結果3秒未満です。
可用性の目安はWeb・MCPとも99.9%、原本の喪失と見過ごされた収集失敗を防ぐことです。いずれも測定・運用で確かめる目標であり、現状の保証ではありません。

主な成果は、一つの問いについて、正確な理解・限界の認識・異なる条件の理解が前進したかで評価します。
任意の評価参加者の閲覧前後を確認する「検証付き問い前進率（QPR）」等を使い、採点方法・対象・版・未回答を明示します。具体的な評価契約はリデザインプランに置きます。
参加者内の結果を全訪問者の理解率に外挿せず、未計測は0としません。クリックや滞在時間だけで理解を推定しません。

問いへの到達、必要なときの再利用、検索成功、原典追跡は別の補助指標にします。毎日読むことや多く回遊することを求めません。
問いの鮮度、訂正時間、維持工数も追い、確認できる範囲で公開内容を広げます。読者の閲覧・回答・連絡先を政治活動へ渡しません。
データは出典数、観測値数、地域範囲、更新状況、確認済み比率を、MCPは成功率、引用率、エラー率、応答時間、費用を追います。

## 長期的なv1の到達条件

現在の公開β版とは分け、以下を長期的な到達条件とします。
50指標・30課題等は網羅性の目安です。件数や機能がそろうことに加え、問いへの有用性と維持可能性を確認します。

1. 横浜の主要50指標を時系列で取得できます。
2. 18区を同じ指標・定義で比較できます。
3. 主要30課題が根拠付きで整理されています。
4. 全事実から原典の該当箇所へ遡れます。
5. 市の予算・決算を検索できます。
6. 一部の領域で政策・予算・成果を根拠付きで追跡できます。
7. 横浜・神戸・福岡を、定義をそろえて比較できます。
8. AIが横浜について一次情報付きで回答できます。
9. 同じ公開情報と問い合わせ機能をMCPから利用できます。
10. 未公開候補が公開データへ混入しないことを検証できます。
11. AIの事実誤認に対する回帰テストをCIで実行できます。
12. 主要な争点から下位の問い・根拠をたどり、元の問いで分かることと残ることを説明できる体験を、市民の利用で確認しています。
13. 公開する問いに担当・確認期限・訂正履歴があり、複数の更新と評価を通じて維持可能性を確認しています。

最初の統合例は、一つの争点から人口等の下位の問いへ進み、具体的な比較と根拠を確かめ、元の争点へ戻る流れです。
人口の一問を原本・検算・説明・比較・更新まで通すことと、争点の理解が前進することを別々に検証します。
必要に応じて予算・過去政策・他都市比較へ広げ、公開済みの答えと証拠をWeb・MCPで共有します。
市民の操作・理解テストと継続利用の評価は、機能の実装とは別に[開発計画](PLAN.md)の受入条件で確認します。

## 対象外

独自LLM、初期段階の巨大Graph DB、全自治体対応、SNSの網羅的収集は目指しません。
有権者個人DB、政治的嗜好の推定、説得されやすさのスコア、属性別の政治メッセージ最適化は提供しません。
横浜の履歴、構造化データ、地理、政策・予算・成果、引用、人間による確認を深めることを優先します。

## 有権者として考えるための基礎記事（2026-09-07追加）

争点記事から生まれる疑問に応じて、市長・議会・国等の権限、公約の費用と財源、実績と効果の違い、価値の優先順位、投票方法、投票後の点検を扱う短い記事を用意します。具体的な打線と制作順はREDESIGN-PLAN第6.6節を正本とします。

知識を順番に修了することを投票の前提にせず、必要なときに読み、元の政策の問いへ戻れる構成にします。投票先や政策の優先順位をサイトが決めるのではなく、本人が判断条件を言葉にできることを支えます。
